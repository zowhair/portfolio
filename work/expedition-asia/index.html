Case study 03 · Client work

Expedition Asia

The website and content system for a trekking and tour operator based in Skardu, Pakistan, guiding in the Karakoram since 2003. The team publishes tours, itineraries and journal posts and handles booking enquiries without needing a developer.

Role
Sole developer: design build, CMS, admin, SEO, hosting and ongoing support
Timeline
First site early 2024; CMS and admin 2026; redesign and move to a new server in autumn 2026
Stack
Next.js 14, Prisma 7, PostgreSQL 17, NextAuth, Nodemailer, Docker, Caddy
Links
expeditionasiaa.com ↗
Results
  • Tours, itineraries, bookings and blog all editable by the team in their own admin
  • Lighthouse on mobile: SEO 100, accessibility 97, best practices 96
  • Runs in Docker beside other apps on a shared server, with CPU and memory limits

The problem

A catalogue that changes every season.

Expedition Asia runs trekking, cultural, mixed and special tours, from K2 Base Camp to helicopter safaris. Prices, departures and itineraries change every season. The first version of the site kept tours in code, so every price update or new trip went through me. That was slow for the team and a poor use of a developer.

Enquiries also arrived in several places, by email, WhatsApp and forms, with no single list of who had asked about what.

Architecture

A small CMS shaped like the business.

The site is a Next.js App Router app on Postgres through Prisma. Instead of a generic headless CMS, the data model mirrors how the team thinks about their work:

  • Tour: a unique slug, one of four categories, and a published flag, so drafts never reach the public site.
  • Itinerary day: ordered days, each with its own steps, deleted together with the tour.
  • Booking: every enquiry is stored and moves through new → contacted → confirmed or cancelled. The office also gets an email.
  • Journal post: articles with cover images and a published flag.

The admin uses credential login with hashed passwords. There's no sign-up page; admin accounts are created by a script, which leaves one less public form to attack. Public pages only ever query published content.

Hard problem 1

Moving from hard-coded pages to a CMS without breaking anything.

Problem
Every tour and post lived in static data files that the components read directly, and the live site's URLs were already indexed by search engines.
Decision
I wrote a one-off seed that loaded the existing tours and posts into the new tables, then switched the pages to the database while keeping the same slugs and URLs. The legacy field names stayed inside the product components so the migration didn't turn into a rewrite.
Result
The team now adds tours, changes prices and publishes journal posts on their own, and the URLs search engines already knew kept working.

Hard problem 2

A good neighbour on a shared server.

Problem
In 2026 the site moved to a new server it shares with other production apps behind one reverse proxy. A noisy or misnamed container on that box can slow down, or even take over, its neighbours.
Decision
The site runs as its own Docker Compose project with explicit CPU and memory limits and log rotation, and publishes no ports. The proxy reaches it through a project-prefixed network alias that can't collide with other apps. Images are built on my machine, tagged with the git commit and shipped to the server, so the server never compiles anything. The build doesn't need a database, which keeps it reproducible.
Result
Deploys are a single script, rollbacks mean running the previous commit's image, and the site's load stays within its own limits.

What's next

Images first.

  • Image pipeline. The site is photo-heavy, and its mobile Lighthouse performance score is 46. Large original photos are resized on demand by a CPU-limited container. Resizing them once at upload and serving fixed sizes from a CDN is the biggest win available.
  • Enquiry tracking. Bringing WhatsApp and email enquiries into the same booking list as web forms.
  • Tests around the booking flow and the admin, which currently rely on manual checks.
