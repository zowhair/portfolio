Case study 01 · Founder-led SaaS

Akteora

A multi-tenant testimonial platform. Customers record video, audio or text from a link with no sign-up. Businesses approve them and publish them as website widgets, a public wall, or captioned reels in three aspect ratios. AI picks the strongest moments but never writes a word.

Sole founder and engineer: product, architecture, code, infrastructure
Timeline

Stack

The problem

Praise is easy to get and hard to use.

Small businesses and agencies hear good things from customers all the time, in emails, DMs and on calls. Turning that into something they can publish is the hard part. Customers won't install an app or create an account to leave a testimonial. Editing a phone video into a captioned clip takes hours.

Existing tools mostly solve the collecting. The obvious next step, letting AI "improve" what the customer said, became a legal problem in October 2024. The US FTC's rule on consumer reviews bans AI-generated testimonials, and it covers the platforms that help make them. I wanted the editing done automatically without changing anything a customer said.

My role and constraints

One person, part-time, one small server.

I built Akteora alone. That covers the product decisions, sixteen written architecture decision records, the code and the operations. The constraints shaped every decision:

  • One VPS with two CPU cores, shared with other sites. FFmpeg will happily use every core it can get.
  • A recording page that has to load fast on a phone with a weak connection, because a customer who gives up is a testimonial lost for good.
  • No team to catch mistakes, so the rules that matter had to be enforced by types, lint rules and CI rather than by memory.

I planned the build as a sequence of small work orders, each with acceptance criteria. Then I implemented them one at a time with AI coding tools (Claude Code), and CI gates acted as the referee: nothing counted as done until lint, tests, build and the bundle-size check all passed.

Architecture

A modular monolith with media on its own path.

There is one API process, one worker process, Postgres and Redis. I chose this over microservices because one person can't afford distributed-systems overhead before the first customer. The boundaries still live in code: domain logic is a pure package with no I/O. Only the database package can touch the database, and every query in it requires a tenant context. Importing the query builder anywhere else is a lint error.

A testimonial moves like this. The browser asks the API for a presigned upload URL, which is locked to a content type and size. It then streams the recording straight to object storage while the customer is still talking. The API only ever handles two small JSON requests and one row write per submission. The worker picks the file up and does the rest: it transcodes, transcribes with word-level timings, extracts sentiment and themes, and publishes.

Hard problem 1

Video rendering on two cores without slowing the website.

Problem
A reel render runs FFmpeg for minutes: cutting clips, normalising loudness, burning captions, encoding three aspect ratios. The same two cores process every new testimonial and serve the recording page's two-second target.
Options
Renders as low-priority jobs on the main queue; a second server; or a shared CPU gate between two queues.
Decision
The worker gets one core and a concurrency of one. The API gets no CPU cap so it can burst. A separate render queue shares an in-process CpuGate with the media queue. A new testimonial always goes first. A render gives its slot back between stages (each cut, each card, each encode), so an incoming testimonial waits at most one stage. While it waits, the dashboard shows the render as "paused".
Trade-off
Renders take longer when traffic is busy, and the gate only works within one process. Moving to several workers means moving it into Redis, which is already planned.
Result
API health checks stayed under 150 ms during a real transcode in production. Every stage's output is cached under a hash of its inputs, so swapping one clip re-cuts only that clip. A ratio whose inputs didn't change isn't encoded again.

Hard problem 2

Keeping customer traffic away from the API.

Problem
Widgets sit on customers' own sites: a Shopify store during a sale, a landing page in an ad campaign. If every page view called my API, their traffic spikes would become my outages, and my outages would break their pages.
Options
An API endpoint cached at the edge; a Cloudflare Worker assembling data per request; or prebuilt static documents.
Decision
Each widget is a static JSON document in the public bucket. The worker rebuilds it whenever something it shows could have changed, and only writes it when its SHA-256 differs. A bulk approval of 100 testimonials is one rebuild, debounced into a five-second window per organisation. The embed snippet reserves the widget's height before the script loads, and the script draws inside a shadow root.
Trade-off
Changes are prompt but not instant: a few seconds to rebuild, then up to a minute of browser cache. Changing a widget's layout means pasting a new snippet.
Result
Cumulative layout shift measured at 0. The script is 6.3 KB gzipped, sets no cookies and makes no third-party requests. Widgets keep working with the API, the database and the worker all down.

Hard problem 3

Tenant isolation that also gives you a free test mode.

Problem
Agencies manage many brands, and integrators need a sandbox. The usual approach is a livemode flag on every table. That would have meant around 25 tables and every query touching them, and one missed filter leaks data between modes.
Decision
A test API key belongs to a sandbox organisation linked to the live one. Every repository already filters by organisation, and a test suite already proves no organisation can see another's rows. So test and live data are separated by the same mechanism that separates customers, with no query changed.
Trade-off
A sandbox is a real organisation row, so jobs that loop over all organisations must skip sandboxes where it matters. Test-mode media is really processed, with small caps on usage.
Result
Test mode behaves exactly like live mode by construction. Adding a table needs no test-mode work beyond the isolation test it already needs.

Hard problem 4

Three bugs that only showed up in production.

Another site took over my domain. All the sites on the server sit behind one Caddy reverse proxy on a shared Docker network. On 6 October 2026, another project's container, also named web, answered to that name. Docker's DNS handed Caddy whichever container it found first, and akteora.com started serving the wrong site. The fix: Caddy now proxies only to project-prefixed network aliases that can't collide. The other sites on the server follow the same rule.

A rate limit that never fired. The per-organisation limit ran in a guard before authentication. It never knew which organisation was calling, so every request was limited by IP address only. I moved key- and organisation-level limits to after authentication: 300 requests a minute per key and 600 per organisation. Unknown keys from one address back off exponentially.

Client IPs that could be faked. Caddy trusted X-Forwarded-For from private address ranges. On a shared network, any container could claim any IP and slip past per-address limits. Nothing legitimate sits in front of Caddy, so I removed the trust entirely.

The AI part

AI selects timestamps. It never writes testimonial words.

The trust rule

Every frame and every caption in a reel is something a real customer actually said. The database schema and the validation enforce this; it isn't just a policy.

Transcription uses OpenAI's whisper-1. I chose it over newer models because it's the one that returns word-level timestamps, and the whole reel editor works on word boundaries. Sentiment and theme tags come from gpt-4o-mini on their own queue.

Choosing soundbites works like this:

  • The model receives transcripts with word timings and returns only {submission_id, start_ms, end_ms, reason}. The reason is shown to the operator in the editor and never appears in the video.
  • The prompt tells the model the transcripts are untrusted public input and that any instructions inside them must be ignored.
  • The prompt is versioned, so every clip can be traced back to what chose it.

The output is checked, not trusted. Each span must sit inside the real recording, start and end exactly on word boundaries, run 3 to 15 seconds, and use each testimonial at most once. A failing answer is sent back once with the reasons. A second failure, or no model at all, falls back to a deterministic rule that picks the densest span. A reel always renders.

Captions are the transcript's own words, burned in with libass and also offered as a .vtt file. They are never regenerated or paraphrased.

Text tidy-up (removing filler words, fixing punctuation) is stored as a separate revision. It can't be used until the customer approves it on a before-and-after diff before they submit. It's also rejected automatically if it changes the length too much or introduces names that weren't in the original. Originals are immutable through a database trigger, and one function is the only way to read displayed text. Operators can hide or delete a testimonial but can't edit the customer's words through any route.

Cost and testing. Transcripts sent to the model are capped at 2,000 words each, and each reel needs one selection call, so the model bill stays small. Whisper is billed per audio minute ($0.006 at list price), so a one-minute testimonial costs well under a cent to transcribe. In CI, the whole AI path runs against a local fake server that speaks OpenAI's protocol, so tests never pay for or depend on the model.

Reliability, security and operations

Small box, real operations.

  • Deploys: Docker Compose behind Caddy with automatic TLS. Readiness checks test Postgres and Redis, not just "process alive", so a deploy can't cut over to a container that only serves errors. Database migrations fail safely before cut-over.
  • Backups: scripted backup and restore, tested by restoring into a scratch database.
  • Server: firewall, fail2ban, key-only SSH and unattended security upgrades. The queue dashboard is reachable only through an SSH tunnel.
  • Webhooks: signed with HMAC-SHA256 and stored before sending. Retries follow a fixed schedule over about 20 hours, and an endpoint is disabled after 24 hours of continuous failure. Every delivery is protected against SSRF: HTTPS only, public addresses checked on every connection, no redirects.
  • API keys: stored as SHA-256 hashes and limited to eleven scopes. Each route declares its scope in one decorator, which also writes the OpenAPI spec, and a test fails if any route is left undecided.
  • Consent and privacy: consent text is stored word for word with each testimonial, and the audit log is append-only. IP addresses are hashed, and logs carry no personal data. Erasing a customer also removes every reel and public copy they appear in.
  • Payments: billing sits behind a provider interface. When two payment providers declined the store, switching to Stripe meant changing one module.
  • Dependencies: a November audit took production dependencies from 4 critical and 17 high advisories to 0 critical, with 2 high left in dev-only tooling.

Results

Where it stands.

Akteora is live at akteora.com in early access, with a free plan. Its Shopify app is being submitted to the Shopify App Store. The engineering results, all measured:

  • Recording page: 23.6 KB of gzipped JavaScript against a 40 KB budget that fails CI if exceeded. A lint rule bans React and analytics imports there.
  • Public testimonial walls: Lighthouse 100/100/100 on desktop and 95/100/100 on phone (performance, accessibility, SEO).
  • Widget: 6.3 KB gzipped, zero layout shift, no cookies.
  • Shared 2-core server: API health under 150 ms while FFmpeg transcodes.
  • About 1,700 automated tests, including Playwright end-to-end runs against the real stack and visual snapshots in both themes.
  • A public REST API with 11 developer guides, a docs site and a typed SDK.

What I'd do differently

Next time, and next.

  • Put it in front of real users sooner. I built the public API, webhooks and SDK before the first customer interviews. The engineering holds up, but a few weeks of customer feedback would have changed the order I built things in.
  • Test on real phones earlier. The recording page has 16 end-to-end tests in CI, but iOS Safari and Android Chrome need their own device pass, because MediaRecorder behaves differently on each.
  • Build an evaluation set for soundbite selection. Today the model's spans are validated for correctness, not judged for quality. The next step is a small labelled set of transcripts and a score for each prompt version.
  • Move the CPU gate into Redis once renders need a second machine.
