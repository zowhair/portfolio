Case study 02 · Marketplace

BookGB

A booking platform for Gilgit-Baltistan, Pakistan. Travellers find hotels and guest houses, rent a car or jeep with or without a driver, and join guided trips, booking directly with the local people who run them.

Role
Product and engineering: traveller web app, host dashboard, API integration, deployment
Timeline
First version July 2025; rebuilt on Next.js in 2026; redesigned November 2026
Stack
Next.js 16, React 19, TanStack Query, Redux Toolkit, React + Vite dashboard, REST API, Docker
Links
bookgb.com ↗
Results
  • Three kinds of listing (stays, vehicles, trips) behind one search
  • Lighthouse on mobile: SEO 100, accessibility 97, best practices 96
  • Destination guides for nine areas, each with its own metadata and structured data

The problem

Great places, hard to book.

Gilgit-Baltistan draws travellers to Hunza, Skardu, Fairy Meadows and the road to K2. Most of the people who host them are small: a family guest house, a driver with a jeep, a local guide. They're reached by phone, WhatsApp or word of mouth. Travellers can't compare options or see prices, and hosts can't be found by anyone who doesn't already know them.

The big booking sites don't fit either. They list few of these hosts, and they ask for online card payments that many local providers don't take.

Architecture

Two front ends on one booking API.

The traveller site is a Next.js App Router app. Search and listing data come from a REST booking API through TanStack Query, and Redux Toolkit holds the search state that crosses pages. Hosts, drivers and operators manage their listings in a separate React + Vite dashboard with role-based navigation and a verification queue for new rooms and vehicles. Both are Docker images deployed to a VPS.

Product decision: book direct, confirm with the provider. A booking request goes to the host, who confirms it, and prices are shown in rupees. That fits how the region already works, where many providers deal in cash and confirm by phone. It keeps the platform from being a payments business on day one. The trade-off is that availability is confirmed by a person, not guaranteed instantly. Verified badges and vehicle inspection scores help build the trust that instant payment would otherwise provide.

Hard problem 1

One search over three different things.

Problem
A stay is searched by dates and guests, a vehicle by seats, bags, transmission and whether it comes with a driver, a trip by departure. Each has different detail pages, prices and filters.
Decision
One search bar with a mode switch, separate typed request models for each listing type, and shared card and listing components where the shapes really are the same. Detail pages stay specific to each type.
What I found
I checked every call the web app makes against the API's OpenAPI spec (111 endpoints, 41 schemas). All matched except one: vehicle search was typed to accept the stay request model, so vehicle filters like seats and transmission could be silently ignored. That kind of drift is invisible in the UI, because the filters look like they work. Checking the client against the spec is now part of how I change it.

Hard problem 2

Getting found, by people and by AI assistants.

Problem
The first version was a client-rendered React single-page app. Search engines and link previews saw an almost empty page. That matters for a travel site, where people start by searching "Hunza hotels" or asking an assistant where to stay.
Decision
I rebuilt the site on Next.js. Every listing and destination page is server-rendered with its own title, description and Open Graph image. The site also generates a sitemap, robots rules and structured data, and has an llms.txt summary for AI assistants. Destination photos are Creative Commons images, each credited in the caption and on a credits page.
Result
On mobile, Lighthouse scores the home page 100 for SEO, 97 for accessibility and 96 for best practices.

What's next

Faster on mountain networks.

  • Performance on weak connections. Mobile Lighthouse performance is 64, with a 3.2-second largest paint. Many visitors are on patchy mobile data in the valleys, so smaller hero images and less client JavaScript on the first page are the next priority.
  • Instant availability for hosts who keep their calendars up to date, alongside request-to-book for everyone else.
  • Contract tests that run the API spec check in CI instead of by hand.
